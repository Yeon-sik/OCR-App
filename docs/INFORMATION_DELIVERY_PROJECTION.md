# 범용 정보 직접 전송과 검토 후 실제 기록 반영

기준일: 2026-11-07 (Asia/Seoul). 각 앱의 feature branch `feat/information-delivery-projection-20261106`, `.worktrees/universal-information-intake`에서 구현했다. 운영 DB 적용, 로컬 앱 검증, 웹 배포, 물리 기기 설치는 별도 상태다. 증거와 산출물은 [최종 검증](validation/2026-11-07-information-delivery-projection.md)을 참조한다.

## 사용 흐름

1. OCR Windows 또는 Android의 정보 보관함에서 원문을 구조화하고 소유 앱을 검토한다.
2. **직접 전송**에서 대상 앱 연결을 설정하고 로그인한다. 프로젝트·계정을 확인하고 체크한 뒤 보낸다. `information-record.v1`의 검토된 원문만 해당 앱의 비공개 검토함 RPC로 전송한다.
3. CashOS와 PriceTrace는 로그인한 계정의 정보 보관함에서 수신 자료를 확인한다. Fitness와 HealthTrace는 정보 검토함의 원격 수신에서 서버 계정과 로컬 프로필을 명시적으로 연결하여 가져온다.
4. 수신 앱에서 실제 기록 종류를 선택하고 빠진 필수값·단위·시간·대상 identity를 검토한다. 반영 미리보기와 계정/프로필을 확인하고 명시적으로 승인한다.
5. 해당 앱의 기존 실제 기록과 통계에 반영된다. 원문은 그대로 남고, 반영 이력에 원문 지문·검토한 mapping·생성한 native ID가 저장된다.

OCR의 전송 완료는 **검토함 도착**을 의미한다. 수신 앱의 실제 기록 반영 완료로 표시하지 않는다. 원문 파일 바이트 전체를 자동 업로드하지 않으며 구조화 payload에 포함된 출처 문구·참조만 전달한다. 임의 PDF·음성·영상의 자동 이해를 보장하는 기능도 아니다.

## 이번에 반영 가능한 실제 기록

| 소유 앱 | 명시적 검토 후 반영 | 그대로 보관하는 범위 |
|---|---|---|
| Fitness | 체중, 식사, 시간 기반 운동, 세트·횟수·중량 기반 운동 | 지원되지 않는 활동 구조 또는 필수 단위·수치 미상 |
| CashOS | KRW 수입·지출과 캐시백, 실제 소유 계정·분류 | 외화 환산, 투자 lot, 이체, 대출 잔액 등 전용 계약 필요 자료 |
| PriceTrace | 검증된 소매 상품·포장과 승인된 판매처에 대한 날짜·KRW 가격 | 미검증 identity, 서비스·메뉴 등 미지원 공개 변환 |
| HealthTrace | 증상 관측, 기존 건강 제품의 복용/건너뜀, 수면 | 임의 검사·질환 등 별도 native adapter가 필요한 자료 |

범용 `*.observation`도 사용자가 반영 종류를 선택해 변환할 수 있다. 이름이나 record_type만으로 의미·단위를 확정하지 않는다. 미상 영양값을 0으로 만들지 않는다. 기존 기록을 덮어쓰는 체중 충돌 등은 거절하여 원래 기록을 유지한다.

PriceTrace는 원문을 비공개로 유지한다. 공개되는 정보는 정확한 상품·판매처·관측일·가격으로 제한한다. 승인된 판매처가 없으면 이름·지점/식별·공개 근거 URL·비공개 근거를 신청하고 기존 관리자 권한의 검토를 거친다. 사용자 편집 가능한 `user_metadata`는 관리자 권한이 되지 않는다. 판매처 승인과 가격 공개 승인은 별도다.

## 소유 경계와 실패 처리

- OCR은 원문과 전달 이력을 소유한다. 네 앱의 실제 도메인 기록을 직접 생성하지 않는다.
- 활동·섭취·체중은 Fitness, 개인 금융은 CashOS, 유상 대상과 가격은 PriceTrace, 수면·복용·증상은 HealthTrace가 소유한다. 다른 앱 ID는 참조이며 쓰기 권한이나 새로운 사실을 만들지 않는다.
- 계정/프로젝트 변경 시 확인을 다시 요구한다. HealthTrace 인증 저장소는 CashOS 세션과 분리한다. 로컬 프로필 연결도 명시적으로 확인한다.
- OCR은 요청 전 전송 시도를 기록한다. 응답 유실·중단·서버 원문 불일치는 미확정/재시도로 남긴다. 동일 UUID 재전송은 서버에서 중복 저장하지 않는다.
- 수신 앱은 native 기록·반영 영수증·검토 상태를 같은 DB 트랜잭션에 저장한다. 어느 단계든 실패하면 모두 되돌린다. 이미 반영된 같은 mapping은 기존 결과를 반환한다.
- 같은 원문을 파일과 서버로 각각 받아도 native 기록은 중복 생성하지 않는다. 이미 반영된 정정 계열의 조상·자손·형제는 새 사실로 합산하지 않는다. 조상 미수신·순환·과도한 깊이는 먼저 해결해야 한다.
- 보관한 자료는 검토 대기로 명시적으로 되돌린 후 신규 반영한다. 기존 반영 이력은 보관 후에도 재조회할 수 있다. 반영 이후 정정은 기존 native 기록의 수정 절차로 처리한다.
- 서버와 클라이언트의 JSON 정렬 방식이 다를 수 있으므로 서버 지문과 로컬 지문을 구분한다. 원문·정밀 십진수·중첩 JSON은 보존한다.

## 주요 계약과 운영 범위

공통 wire 계약은 `contracts/information-record.v1.md`다. 각 앱의 mapping 계약은 Fitness `contracts/fitness-native-projection.v1.md`, CashOS `specs/25_INFORMATION_PROJECTION.md`, PriceTrace `docs/contracts/INFORMATION_PRICE_PROJECTION_V1.md`, HealthTrace `docs/INFORMATION_DELIVERY_PROJECTION.md`에 있다.

새 migration은 추가형으로 적용하고 이미 운영에 적용한 파일은 수정하지 않는다. 로컬/원격 migration 이력이 다른 저장소는 전체 bulk push 대신 실제 원격 이력을 가져온 staging에 새 파일만 넣어 적용한다. 데이터 삭제, 기존 사용자 역할 변경, 이름 기반 identity 자동 승인, 웹 호스팅 배포나 물리 기기 교체 설치는 이 작업에서 수행하지 않았다.
